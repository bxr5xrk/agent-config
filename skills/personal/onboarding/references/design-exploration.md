# Visual exploration contract

For `product_brand`, do this after the brand foundation is approved and before the final UI kit or feature implementation. Skip the multi-option contract for `lightweight_site` unless the user explicitly requests alternatives. First identify the core task and comparable content. Research supplied links first, then original product sites, Curated/Lapa for marketing and Mobbin for task flows. Verify actual pages; a search thumbnail is not a full UX review. Use X/community posts for discovery, not evidence that a design technique works better.

Default **6** options; honor any requested count in **5–10**. Give stable IDs A–F. Each must visibly differ on at least three substantive axes: composition, information hierarchy, navigation pattern, typography, image treatment, density, motion or brand expression. Color swaps do not qualify. Keep the same product, core task, content and desktop viewport across options; show mobile treatment for all options or at least the shortlisted pair before selection.

Each option applies the same approved name, positioning and core promise, and contains:

- Actual rendered visual: image-generated mockup, browser-rendered lightweight prototype, or an inspected reference screenshot with an honest label.
- Main screen + key interaction/state; real product vocabulary, plausible data clearly marked as sample.
- Reference URL(s) and what is borrowed; don't copy branding/assets without permission.
- One-sentence fit, one tradeoff, typography/palette/density/navigation decisions.

Display all options in a comparison board and let the user enlarge each; provide a true side-by-side view for 2–3 shortlisted options. A selection shelf without comparison does not satisfy this stage. Labels and controls must remain readable at preview size. Offer combinations such as A's layout + D's type + F's imagery; document the precise combination rather than synthesizing silently.

Ask one selection question after the visible board. Do not proceed to the product UI or UI kit until selected, unless the user explicitly delegates. Research and backend planning independent of that choice may continue. If generation or screenshots are blocked, state the missing visual evidence and provide accessible references; do not claim that a prose list fulfills the visual gate.

Use image_gen for generated/editable raster mockups; use actual browser prototypes when the decision is mainly interaction. Read the relevant available skill first. Do not instantiate 6 production apps; cheap visual prototypes are enough. Don't assume a particular frontend aesthetic must be reused across future products.

Persist `options`, `visual_artifact`, `source_urls`, `tradeoffs`, `selected_ids`, `combination`, and `selection_status` in the project's design notes. Store only approved reusable taste guidance in the skill if the user explicitly asks to update it.
