# Automatic learning during ordinary work

The user never needs to invoke a learning skill. Apply this throughout an active brainstorm, build, designer, frontend or backend conversation, including follow-up messages that contain no skill command.

Recognize a correction when the user rejects a result, demonstrates a better alternative, points out a repeated mistake, or asks to remember a decision. First fix the actual task and reconcile its project documents. A palette, product fact or exception for this project stays local; one correction must not silently become a universal taste rule.

Automatically use the [internal learning procedure](../internal/learn/ROLE.md) when the correction supports a transferable technique or an explicit broader preference. Stage the candidate using its helper; do not merely say that it was remembered. Repeated evidence should revise an undecided candidate or strengthen an existing rule, not create duplicates. If the lesson already exists, diagnose why it was missed before proposing more instructions.

The closeout owner collects corrections from delegated workers. Curate, test and prepare the exact candidate batch as part of the current work when sufficient evidence is available. Present a compact batch at a natural stopping point; avoid an approval interruption after each small edit. The user's chosen policy is batch approval before global publication. Ordinary rejection or “remember this” triggers capture; it does not approve unrelated pending rules or invent global scope. Continue the requested fix while a batch awaits approval.

At the beginning of later work, automatically recall approved applicable lessons through the internal helper. Local project decisions still take precedence where their scope differs. No daemon, separate `$learn` command, model-weight training or background task is required. Only claim a lesson was saved or published after the actual write succeeded.
